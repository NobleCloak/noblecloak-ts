# @noblecloak/spec

## 0.10.0

### Minor Changes

- 5cf6237: Contract rev 15 (release `contract-v1-rev15`): **per-approval actions**. An `Approval` can now say which actions the reader may take on this approval, typed, with the deployment's own wording and the inputs each takes. Until now the only source was the deployment-wide `Capabilities.resolutions`. Every addition is optional on the wire, so a rev 14 server's responses still validate against rev 15's response schemas, and nothing a rev 14 server answers changes.

  **`Approval.available_actions`**

  - An array of `ApprovalAction`, optional. Present only on `GET /v1/approvals/{id}`, only while the approval is `pending`, and only to a reader who may resolve it, as `Approval.preview` is; absent on a list row, a stream event and for every other reader. Every `resolve` action's `resolution` is one of `Capabilities.resolutions`. On a deployment that does not list `approvals.available_actions`, absent means the deployment does not say, and a client derives approve and deny from `Capabilities.resolutions`, as before. On a deployment that lists it, absent means no action for this reader, and a client derives none. Being listed is not authorisation: resolving still decides eligibility when it is called.
  - `ApprovalAction` is `{ id, kind, label, resolution?, inputs }`, a closed object. `id` is unique within the list. `kind` is an open enum whose documented value is `resolve`; a client ignores a kind it does not know. `resolution` is the closed `ResolveResolution` and is present exactly when `kind` is `resolve`. `inputs` may be empty.
  - `ApprovalActionInput` is `{ name, type, label, required, max_length? }`, a closed object. `type` is an open enum whose documented value is `text`; a client does not offer an action that has an input of a type it does not know. The input named `reason` fills `ResolveRequest.reason`; any other name is a member of `ResolveRequest.input`.

  **Feature `approvals.available_actions`.** Listed in `Capabilities.features` by a deployment that sets the member; it is in the `FEATURES` a scenario may require.

  **Mock and conformance**

  - The mock advertises the feature wherever it serves approvals, and lists an Approve and a Deny action (for the resolutions it serves) with the optional input `reason`, on the single read of a pending approval to a reader who may resolve it. New breaks `available_actions_shown_to_all` (eligibility and scope), `available_actions_shown_when_resolved` (pending), `available_actions_shown_without_resolve_scope` (scope) and `available_actions_shown_to_members` (eligibility, for a member), each with a row of the broken-mock matrix.
  - New scenarios in `32-rev15-available-actions.yaml`, all gated `features: [approvals.available_actions]`: `available-actions-for-approvers`, and the negatives `available-actions-hidden-from-others` (the person who opened it, a member who is not eligible, and the approver once it is resolved) and `available-actions-hidden-without-resolve-scope` (also gated `advertises: [user_resolve_scope]`).
  - A deployment that vendors the scenarios and runs them nightly adds the three new ids to its expected-skips until it serves the feature.

  **Quarterback calls**: QC1 visibility mirrors `preview` (single read, pending, a reader who may resolve it); QC2 `kind` and input `type` are open enums; QC3 the input name `reason` maps to `ResolveRequest.reason`.

  `@noblecloak/client`: regenerated (`ApprovalAction`, `ApprovalActionInput`, `Approval.available_actions`).

- 529a179: The package knows one document, `openapi.public.yaml`. `MockOptions.face`, `Target.face` and `Report.face` are
  removed, and `formatReport` prints `conformance <deployment>: …`. `nc-conform --face public` and
  `nc-mock --face public` are still accepted for this release and ignored with a deprecation line on stderr; any
  other value is a usage error. A deployment that extends the document adds its members to every approval handle the
  mock serves with the new `MockOptions.extendHandle`. The break `undeclared_handle_member` adds a member no schema
  declares to every handle, and every conformance run against the mock now fails a response member the document does
  not declare. `loadFace` is renamed `loadDocument`, and `loadFace` is no longer exported: a caller
  imports `loadDocument` instead.

## 0.9.0

### Minor Changes

- 40c58bd: Contract rev 14 (release `contract-v1-rev14`): a **deployment-applied reference**, a `tool_ref` in the namespace `tool:noblecloak:` that names a change the deployment makes itself when an approval for it is approved, and its first instance, `tool:noblecloak:propose-policy-set`. A person opens it through `POST /v1/approvals`, an administrator approves it, and the deployment registers the agent's tools, binds its service principal and creates and publishes its policies in one step, or applies nothing. Every addition is optional on the wire, so a rev 13 server's responses still validate against rev 14's response schemas, with the narrowing named below.

  **Narrowings (named here)**

  - Registering a tool under `tool:noblecloak:` is now 422 `reserved_tool_ref` on every deployment, and a policy whose `targets` name a reference in that namespace is now 422 `policy_immutable` on create, replace and simulate; a rev 13 server that accepted the first fails the floor scenario `proposal-reserved-namespace`, and a hosted one that serves policies and accepted the second fails `proposal-policy-immutable`, which runs only there. Nothing else a rev 13 server answers changes on the wire.
  - Mock dev token, not the contract: `approver_surface_token` now also holds the administrator role (see Conformance and the mock).

  **Deployment-applied references**

  - **The namespace is reserved.** Registering a tool under `tool:noblecloak:` is 422 `reserved_tool_ref`. A deployment-applied reference is never listed by `GET /v1/tools` and is never decided as an ordinary tool (a decision on it is `deny` with reason `unknown_tool`). Its policy is fixed at `ask`: authoring a policy, replacing a draft or simulating a proposed body whose `targets` name a reference in the namespace is 422 `policy_immutable`, a new problem type (`createPolicy`, `updatePolicy` and `simulatePolicySet` answer it through the new response `UnprocessablePolicyWrite`; `publishPolicy` and the rest keep `UnprocessablePolicyForm`). `importPolicies` never imports such a policy: it lists it under `unsupported`, with a `reason` that names `policy_immutable`.
  - **A deployment says which it applies.** `Capabilities.deployment_applied` lists `{ tool_ref, arguments_schema_ref }`; `arguments_schema_ref` names the schema `action.arguments` must fit. A deployment that does not list a reference answers 422 `approval_unroutable`. `tool:noblecloak:propose-policy-set` is applied only by a deployment that authors and publishes policies of its own (today, hosted). `info.x-noblecloak-deployment-applied` carries the same table, machine-readable. There is no `x-noblecloak-deployment` tag on a reference: that extension tags operations, and the reference is reached through `POST /v1/approvals`, which is `both`.
  - **Stated once** in the API description ("Deployment-applied proposals (rev 14)"): the namespace, the capability, opening, the effect on approval, who approves and the preview.

  **`PolicySetProposal`** (the arguments of `tool:noblecloak:propose-policy-set`, a closed schema)

  - `agent` (`{ id }`, an agent of the organisation, and optionally `principal_id`, a service principal to bind); `tools` (up to 50 `ToolWrite`, `owner_kind: org`, `ext:` references only); `policies` (1 to 50 `PolicySetEntry`: `role` `baseline` or `tightening`, a `rationale` of 1 to 500 characters, a `PolicySetAssessment` and a `PolicyWrite`). A baseline is a `tool_invocation` policy on the one subject `{ role, everyone }` for one tool; a tightening is one on the one subject `{ agent, <agent.id> }` for one tool. No two policies of a proposal have the same target tool and subject (`shape`). A proposed policy's `config` carries `mode` only: any other member (`approver_groups`, `expires_after`, `on_deny`, ...) or an `origin` is `shape` with `member` naming it, because the approver sees the arguments, but what the checks at open and the preview compare is the mode alone (a change to the routing, the expiry or `on_deny` would get no check and no preview line). The whole `action.arguments` fits `limits.approval_arguments_max_bytes` where one is advertised (400 `invalid_request` otherwise); the two caps of 50 keep a typical proposal inside the 32 KiB that a deployment commonly sets.
  - **Refusals at open** are 422 `proposal_refused` (new), with the new `Problem.code`: `not_a_user`, `shape`, `unknown_agent`, `principal_bound`, `tool_ref_in_use`, `target_unknown`, `baseline_exists` and `tightening_looser`. `Problem.member` is widened from `unsupported_policy_form` to `unsupported_policy_form` and `proposal_refused`, and names the part of the body (`action.arguments.policies[1].policy.targets.tools[0]`); which code is reported when several apply is the deployment's choice. `reserved_tool_ref`'s title now names the namespace. No check at open refuses a tightening because a published policy of the same agent already governs its tool (by name or by `all`): such a proposal may open, and approving it never applies it (it is refused with `proposal_refused:policy_conflict`, unless a check run again refuses it first); such a change is made by editing or retiring that policy.

  **`Approval.preview`**

  - Present only on `GET /v1/approvals/{id}`, only while the approval is pending, and only to a reader who may approve it; absent everywhere else, and no part of `arguments`. `ApprovalPreview` is `{ simulations, loosening }`: `simulations` has one `{ tool_ref, result: SimulateResult }` for each tool the policies govern (in order of first appearance), composed for the agent with every proposed body beside the policies in force and the proposal's tools registered; `loosening` lists each baseline looser than the mode the deployment's default gives the tool, as `{ tool_ref, from, to }`.

  **Approving**

  - All or nothing, in the order tools, binding, policies (each created and published, in the order of `policies`). The checks that opening ran are run again against the state of that moment. If any step cannot be applied, nothing is applied: the approval resolves `rejected`, the answer to the approve call is still 200, and the last entry of `resolution_history` has `resolution: rejected`, `by` the administrator whose approval the deployment refused to apply, and `reason` `proposal_refused:<code>`, where `<code>` is a code above or `policy_conflict`. No new member records it: `HistoryEntry.reason` now says so. A success is `approved` and at once `consumed`; nothing resumes (the continuation is `mcp_held`). Denying applies nothing.
  - **Who approves.** An administrator of the organisation, under the deployment's own eligibility rules; the person who opened the proposal approves it only from the approver surface (`Capabilities.self_approval_from_approver_surface`), never with the token that opened it. That is the rule for every deployment-applied reference.

  **Conformance and the mock**

  - **New scenarios** (`31-rev14-policy-set-proposal.yaml`, nineteen): `proposal-reserved-namespace`, `proposal-policy-immutable`, `proposal-unroutable-where-not-applied`, `proposal-applied-on-approval`, `proposal-refused-at-approval-applies-nothing`, `proposal-rechecked-at-approval`, `proposal-denied-applies-nothing`, `proposal-preview-is-for-approvers`, `proposal-approver-must-be-an-administrator`, `proposal-self-approval-from-the-approver-surface`, `proposal-refused-not-a-user`, `proposal-refused-bad-shape`, `proposal-refused-config-beyond-mode`, `proposal-refused-agent-and-principal`, `proposal-refused-tools-and-targets`, `proposal-refused-baseline-exists`, `proposal-refused-tightening-looser`, `proposal-import-skips-reference` and `proposal-arguments-bound`. Each that applies a proposal unbinds the agent and retires its policies in `cleanup`; a tool it registers stays registered, under a reference of its own. A scenario gains the optional field `arguments_bytes` (the most bytes of arguments it sends: a capability skip where the deployment advertises a smaller `approval_arguments_max_bytes`), and `deployment_applied` joins the capability members that `advertises` may name (an empty list counts as not advertised).
  - **Mock.** The namespace is reserved; `deployment_applied` is advertised by the hosted mock; opening runs the schema, the rules beyond it and the checks against the state, and stores the preview; approving re-runs the checks, applies against a snapshot that it restores on any failure, and sends the `policy.published` events only once everything is applied. A deployment-applied approval is approved by an administrator only, and the mock's `approver_surface_token` now also holds the administrator role (the session of an administrator in the approvals module). New break flags, each with a row of the broken-mock matrix: `reserved_namespace_registrable`, `policy_on_deployment_applied_accepted`, `deployment_applied_listed_as_tool`, `service_principal_can_propose`, `proposal_refusal_code_missing`, `baseline_over_existing`, `tightening_looser_accepted`, `preview_loosening_missing`, `preview_shown_to_all`, `proposal_approved_by_non_admin`, `proposal_effect_partial`, `proposal_recheck_skipped`, `proposal_refusal_reason_missing`, `proposal_deny_applies`, `proposal_not_consumed`, `proposal_config_beyond_mode_accepted` and `proposal_baseline_config_beyond_mode_accepted`; the row of `arguments_bound_not_enforced` also names `proposal-arguments-bound`.
  - **Rev 13 scenario errata (no contract change).** `agent-policy-from-binding-only`, `simulate-set-without-anything-stored` and `unsupported-policy-form-names-member` authored `tool_invocation` policies with an `{ type: organization }` subject and no `serves_policy_subject_type` gate; the mock advertises every subject type, so they passed there, but a deployment that serves no organisation tool subject (hosted COO) could not run them. They now use `{ type: role, id: everyone }` and declare `serves_policy_subject_type: role` (`[role, agent]` for `agent-policy-from-binding-only`, which also authors agent-subject policies); the `duplicate_requests` steps keep `organization`, the only subject that kind takes. `unsupported-policy-form-names-member` also names its tool in `targets`, so a deployment that advertises `targets_all: false` reaches the `member` it checks. The generated scenario `policy-forms-advertised-are-accepted` creates a real `/v1/agents` row for its agent-subject drafts where the deployment serves `agents` (a placeholder id otherwise).
  - `@noblecloak/react` gains two entries in its problem-code table (`proposal_refused` and `policy_immutable` map to `invalid_request`; see its own changeset) and is otherwise unchanged.
  - Docs: `docs/how-to/propose-a-policy-set.md` (Propose a policy set for your agent), and the rev 14 section of the spec README.

  **Quarterback calls** (revisable before merge): QC1 the namespace is a contract concept, with `deployment_applied` and no operation tag; QC2 `PolicySetProposal` and its rules; QC3 `proposal_refused` with `code` and `member`, and `policy_immutable`; QC4 `Approval.preview` is `{ simulations, loosening }` where the brief wrote one `simulation` (a `SimulateResult` is for one call, so a proposal that governs several tools has one for each); QC5 all or nothing, with the refusal in `HistoryEntry.reason`; QC6 an administrator approves, and self-approval follows the approver-surface rule.

  `@noblecloak/client`: regenerated (`PolicySetProposal`, `PolicySetEntry`, `PolicySetAssessment`, `ApprovalPreview`, `Approval.preview`, `Capabilities.deployment_applied`, `Problem.code` and the wider `Problem.member`).

## 0.8.0

### Minor Changes

- d427655: Contract rev 13 (release `contract-v1-rev13`): an agent is bound to one service principal, every caller holds the reserved role `everyone`, a set of proposed policies is simulated without storing any, and `unsupported_policy_form` names its member. Every addition is optional on the wire, so a rev 12 server's responses still validate against rev 13's response schemas. One behaviour changes: `actor.agent_id` no longer selects an agent's policies (below).

  **Agent identity**

  - **The binding.** `PUT /v1/agents/{id}/principal` with `{ principal_id }` binds an agent to one service principal of the organisation, and `DELETE` removes it. Both are for an administrator of the organisation (403 `forbidden` otherwise; a service principal never is one) and are served by both deployments (family `agents`). `principal_id` is the `id` that `Record.actor` and `GET /v1/principals` carry for the service principal; one that names no service principal of the organisation (a user, or a principal of another organisation) is 404 `not_found`; a service principal already bound to another agent is 409 `principal_bound`, a new problem type whose `agent_id` names the holder; `DELETE` on an unbound agent is 204. `Agent` gains `principal_id: string | null`, optional on the wire.
  - **Agent policies apply through the binding only (behaviour change).** On a decision, a record and a simulation without `subject`, the caller holds an agent's policies only if it is the service principal bound to that agent. `actor.agent_id` stays on decisions and records as a display hint and never selects policy: anyone who relied on the hint to have an agent's policy apply must bind the agent's service principal. Nor does the `agent_id` of a run named in `actor.run_id`. `ActorHint`, `Run.agent_id` and the `createRun` text say so. Agent policies only tighten: no composition rule changes.
  - **`Approval.agent`.** When the caller is a bound service principal the approval names the bound agent and the hint is ignored; when the caller is unbound the hint is shown as before.
  - Stated once in the API description ("Agent identity (rev 13)").

  **The `everyone` role**

  - Every caller holds the reserved role `everyone`, a user, an agent or a service principal. A policy may name it as a subject (`{ type: role, id: everyone }`) and it applies to every caller beside the caller's other subjects: the organisation's baseline.
  - It is reserved: a deployment never lets it be assigned, never lists it as a directory role (`GET /v1/principals?type=role` omits it, by its bare key, by an id in the deployment's own form ending in `:everyone` or `/everyone`, and by its display name) and never lets it be created.
  - A simulation as an agent is that agent's policies, `everyone` and the organisation's, and no user's or other role's (this amends the rev 11 text "and no user's or role's"). Simulating as `{ type: role, id: everyone }` gives the baseline.
  - The role key is `everyone`, never `default`: `default` is only a value of `ConsideredPolicies.policies[].source` (a default of the deployment), and the text now tells the two apart. Stated once in the API description ("Reserved roles (rev 13)").

  **Simulating a set**

  - `POST /v1/policies/simulate` (`simulatePolicySet`, family `policies`, both deployments) takes `SimulateSetRequest` (closed: `policies` of 1 to 100 `PolicyWrite`, `action`, and the optional `resource`, `context`, `actor`, `subject`) and answers a `SimulateEnvelope`. It is the route to use when nothing is published. The proposed bodies stand beside what is in force and never replace a stored policy. An entry from a proposed body has `id: null`, `version: null` and the new `proposed_index`; a default of the deployment, which also has a null `id` and `version`, carries `source` and never `proposed_index`. Bodies are validated as `POST /v1/policies` validates them (400 `invalid_request`, or 422 `unsupported_policy_form` with `member`). No administrator is needed except with `subject`. Nothing is written.

  **A structured `member`**

  - `Problem.member`, only on `unsupported_policy_form`: a dotted and bracketed path into the request body as sent (`subjects[0].type`, `config.mode`, `subject`, `policies[2].subjects[0].type`). `detail` stays human prose. The texts that said "`detail` names the member" now say `member` names it, with `detail` as the rev 12 reading.

  **Conformance and the mock**

  - **Reshaped scenarios** (every id kept): `routes-agents` also reads `principal_id: null`; `simulate-as-an-agent` adds a policy on `everyone` that the agent holds, and its gate's `otherwise` now takes `member: subject`, with `detail_matches` still accepted for a rev 12 deployment (a gate's `otherwise` gains an optional `member`).
  - **New scenarios** (`30-rev13-agent-identity.yaml`): `agent-binding-admin-only`, `agent-binding-refuses-a-user`, `agent-policy-from-binding-only`, `agent-policy-not-from-a-run`, `everyone-role-reaches-every-caller`, `everyone-role-not-a-directory-role`, `simulate-set-without-anything-stored`, `simulate-set-stands-beside-stored-policies`, `simulate-set-duplicate-stands-beside-in-force`, `unsupported-policy-form-names-member`. No scenario binds as a service principal: each binds as `admin` with `needs: [admin]`, and unbinds in a scenario `cleanup` that runs whether the steps passed or failed (a scenario gains an optional `cleanup` list of request steps, which may not name a variable saved at or after a gate step, and a step's `expect` an optional `follow_pages` that checks a listing to its last page, and a body predicate `lacks_where_matches` that no element's string member matches a pattern, case-insensitively with `ignore_case`). The generated `policy-forms-advertised-are-accepted` keeps its placeholder agent id: it creates drafts only, so no binding is involved, and creating a real agent would add a requirement on the `agents` family to a scenario generated from `policy_forms` alone.
  - **Mock.** The binding lives on the agent row; the agent arm of the caller's holder is the agent bound to the caller; `everyone` is held by every caller and every simulated subject but the organisation; `POST /v1/policies/simulate` reuses the simulation; every `unsupported_policy_form` carries `member` (and keeps the `detail` prefix). The mock's `decide` still answers from the tool's mode, so the binding and `everyone` are shown through simulate without `subject`. New break flags, each with a row of the broken-mock matrix: `agent_binding_unguarded`, `principal_bound_to_two_agents`, `hint_selects_agent_policy`, `unbound_caller_holds_agent_policy`, `everyone_not_held_by_service`, `agent_subject_loses_everyone`, `simulate_set_replaces_stored`, `unsupported_form_member_missing`, `everyone_listed_as_directory_role`, `everyone_listed_by_prefixed_id`, `approval_names_hinted_agent`, `simulate_set_duplicate_replaces_in_force`, `user_principal_bindable`, `proposed_entry_has_source`, `run_agent_selects_agent_policy` and `set_simulation_reads_hint`. A proposed `duplicate_requests` body stands beside the duplicate-requests setting in force and the tightest applies; a second one is 422 `unsupported_policy_form` with `member` `policies[<index>].kind`; with `subject`, the administrator check runs before the body is validated. A `ConsideredPolicies` entry is a default (`source`) or a proposed body (`proposed_index`), never both, and `Problem.member` has a grammar (a dotted and bracketed path starting at a top-level member).
  - `@noblecloak/react` gains one table entry only (`principal_bound` maps to `conflict`, so its problem-code table still equals the contract's registry; see its own changeset), and its README now says the mock implements revision 13. It is otherwise unchanged: it still sends `actor.agent_id` from its simulation form and reads the subject refusal from `detail`, both of which keep working against rev 13. Reading `member`, using `POST /v1/policies/simulate` and showing `everyone` are a follow-up.

  **Quarterback calls** (revisable before merge): QC1 the binding route and its 403/404/409/204 answers; QC2 the holder rules (the bound service principal only, and as an agent: the agent, `everyone` and the organisation); QC3 `Approval.agent` follows the binding; QC4 the mock's `decide` is unchanged; QC5 the role key is `everyone`; QC6 `POST /v1/policies/simulate` with `SimulateSetRequest`, `proposed_index` and null `id`/`version`; QC7 `Problem.member`; QC8 `everyone` is reserved and never a directory role.

  `@noblecloak/client`: regenerated (`Agent.principal_id`, `AgentPrincipalWrite`, `SimulateSetRequest`, `ConsideredPolicies.policies[].proposed_index`, `Problem.agent_id` and `Problem.member`, the two agent-binding operations and `simulatePolicySet`).

## 0.7.0

### Minor Changes

- ed41848: Contract rev 12 (release `contract-v1-rev12`): how registered browser origins govern CORS, and what a webhook delivery is. Registered origins and webhooks become an administrator's. Every other member it adds is optional, and a rev 11 server's responses still validate against rev 12's response schemas, with the removal of `Webhook.secret` and the narrowings listed below.

  **Browser origins (the preflight model)**

  - **CORS.** A preflight carries no token, so it is answered against the union of the deployment's own admitted origins and every organisation's registered origins; it never reveals which organisation registered one. An actual request carries the token and is checked against the caller organisation's registered origins plus the deployment's own: any other `Origin` is 403 `forbidden`, with no `Access-Control-Allow-Origin` on the response. A request without `Origin` is unaffected. A deployment may admit origins of its own that no organisation registered. Stated once, in the API description ("Browser origins (rev 12)").
  - **Who.** `GET /v1/origins` is open to any principal of the organisation. `PUT /v1/origins` is for an administrator of the organisation (403 `forbidden` otherwise), the rule for authoring a policy.
  - **Exact origins (a new restriction).** A registered origin is `scheme://host[:port]`, the form a browser sends in `Origin`, with no path, query, fragment, trailing slash, userinfo or wildcard, and `https` (`http` only for `localhost` and `127.0.0.1`). The form is canonical: a lowercase host, and no default port (`:443` for `https`). One that is not exact is 400 `invalid_request`, naming it; a deployment never normalises a submitted origin. `OriginsWrite` carries a coarse `pattern` only (the stated rule governs, and `origins-must-be-exact` pins the default port and upper-case host); `Origins` (the read) does not, so a rev 11 deployment's stored origin still validates. The mock's static `--allow-origin` list is unchanged.

  **Webhooks**
