Contract rev 18 (release `contract-v1-rev18`): **role rows, proposals without an agent, and tool grants in `tool:noblecloak:propose-policy-set`**. Four changes to `PolicySetProposal`, so that a set of starter policies is proposed and applied through the same reference as an agent's:

- **`role` rows.** `PolicySetEntry.role` gains `role`: a `tool_invocation` policy for one role of the organisation, with exactly one subject `{ type: role, id: <key> }` (a bare role key, never `everyone` in any case or in a form ending `:everyone` or `/everyone`), one tool and `mode` only. No open-time check compares a role row with the baseline. Instead `ApprovalPreview.ineffective` lists `{ tool_ref, subject }` for each role row whose mode is looser than the tightest mode a policy of `everyone` gives the same tool (a published one, or a baseline of the same set): under tightest-wins that row changes nothing while the policy of `everyone` stands. `ApprovalPreview.loosening` gains an entry with the optional member `subject` for each role row that loosens what its role gets: `from` is what tightest-wins composes for the role now (the published policies of the role, of `everyone` and of the organisation for the tool, or the default), `to` is what it composes with the proposal's baseline and the row, so an empty `loosening` still says that approving loosens nothing. The simulations, as the agent or as `everyone`, do not show what a role row does.
- **`not_entitled`.** A role row needs the entitlement `policies.role_subjects`. Without it the proposal is refused 422 `proposal_refused` with the new `code` `not_entitled`, `member` naming the first role row and `detail` naming the key. Approving checks it again, and a refusal there resolves the approval `rejected` with `proposal_refused:not_entitled`. `Capabilities.entitlements` gains a description and `x-noblecloak-known-values` (`records.verify`, `evidence.export`, `policies.suggested`, `policies.role_subjects`), open-ended; a test pins that every key a route extension names is among them. The 403 problem type `entitlement_required` keeps its meaning (a route the organisation is not entitled to) and no new problem type or `Problem` member is added.
- **`agent` is optional.** A proposal without it carries `baseline` and `role` rows and, optionally, `tools`; its preview simulates as `{ type: role, id: everyone }`. A `tightening` or `tool_grants` without an agent is `shape`. With an agent nothing changes from rev 14. This widens what a request may send: a reader of a proposal's `arguments` may find no `agent`, and such an approval names no agent.
- **`tool_grants`.** Up to 50 distinct references of tools the organisation already holds, granted on approval to the service principal in `agent.principal_id`, which they require (`shape` otherwise). A reference in the `tool:noblecloak:` namespace or among the proposal's own `tools` is `shape`; one that is no tool of the organisation, or a withdrawn one, is `target_unknown` naming `action.arguments.tool_grants[<i>]`. Grants are applied in the same all-or-nothing step, after the binding and before the policies, and a grant that exists is kept. `ApprovalPreview.grants` lists them. A grant is a deployment-applied instruction: the visibility rule of `GET /v1/tools` (`Owner`) is unchanged, and what a grant does beyond that is the deployment's.

`Capabilities` gains the optional member `proposals: { row_kinds, members }`, open-ended arrays with known values (`baseline | tightening | role`; `tool_grants`), the same list style as rev 17's `continuation_kinds`. Absent means what rev 14 accepts: `baseline` and `tightening`, no member. A row kind or member a deployment does not list is `shape`.

A deployment that keeps its own copy of the `PolicySetProposal` text re-copies it and advertises `proposals` in the same change; until then it accepts what rev 14 did and the rev 18 scenarios are capability skips.

**Mock and conformance**

- The mock implements all of it on the hosted deployment and advertises every row kind and `tool_grants`; `MockOptions.proposals` starts it with less. The mock keeps no entitlements per organisation: an open reads the opener's token (the minted `entitled` token now holds `policies.role_subjects`; `creator_user` holds none) and records that set on the approval, and an approval reads the approving token's `entitlements` claim when it carries one, otherwise the recorded set. It records grants in its state and changes no tool's visibility.
- The entitlement is the organisation's, so the scenarios name the organisation each token must belong to: the ones that open a role row as `entitled` and approve as `admin` need `--entitled-token` to be a user of the organisation of `--token` and `--admin-token`, holding `policies.role_subjects`; `rev18-role-row-not-entitled` opens as `other_org`, whose organisation must not hold it. Each first reads `GET /v1/capabilities` with that token and fails there, naming the entitlement, when the organisation is the wrong one.
- Conformance: `proposals` joins the capability members a scenario may name in `advertises`, and the runner reads it from `GET /v1/capabilities`. A scenario may declare `serves_row_kind` or `serves_proposal_member`: it is a capability skip where `proposals` lacks the value, or is absent and the value is not one of rev 14's.
- New scenarios in `35-rev18-proposal-role-rows-and-grants.yaml`: `rev18-role-rows-applied-without-an-agent`, `rev18-tool-grants-previewed-and-applied`, `rev18-preview-names-a-shadowed-role-row`, `rev18-preview-names-a-loosening-role-row`, and the negatives `rev18-role-row-not-entitled`, `rev18-no-agent-no-tightening-no-grants`, `rev18-tool-grants-need-a-principal` and `rev18-tool-grant-unknown-tool`. New breaks: `proposal_role_unentitled_accepted`, `proposal_grants_without_principal_accepted`, `proposal_unknown_grant_accepted`, `preview_ineffective_missing`, `preview_grants_missing`, `preview_role_loosening_missing`.
- `@noblecloak/client`: the generated types gain `PolicySetEntry.role` `"role"`, an optional `PolicySetProposal.agent`, `PolicySetProposal.tool_grants?`, `ApprovalPreview.grants?`, `ineffective?` and `loosening[].subject?`, and `Capabilities.proposals?`.
